# Lark Gateway 语音识别限流重试设计

## 问题

Gateway 已能接收飞书 `audio` 消息，下载语音资源并通过 FFmpeg 转换为 16 kHz PCM。
实际调用飞书语音识别接口时，服务可能返回：

```text
99991400 / request trigger frequency limit / retryable: true
```

`lark-cli` 对失败请求以非零状态退出，并把 JSON 错误信封写入 stderr。现有实现只从
stdout 读取错误信封，并在检查信封前先按退出码抛出通用错误，因此既丢失了限流原因，
也不会执行服务端明确允许的重试。用户最终只能看到笼统的“语音识别失败”。

现场诊断已确认同一条 3 秒语音可以正常下载和转码，故障仅发生在识别 API 阶段。

## 目标

- 正确解析 `lark-cli` 写入 stdout 或 stderr 的 JSON 成功/错误信封。
- 仅对飞书明确标记为可重试的语音识别限流执行有界退避重试。
- 重试期间复用已下载、转码的 PCM 和请求体，不重复下载或转码。
- 重试耗尽后向用户明确说明是飞书语音识别限流。
- 权限、参数、文件、转码及不可重试 API 错误保持立即失败。
- 日志和用户回复不泄露 token、完整错误信封或音频内容。

## 方案

### 错误信封解析

语音模块从 stdout 开始解析 JSON；stdout 为空或不是 JSON 时再解析 stderr。只有对象型
JSON 才作为 API 信封。`ok: false` 的信封必须先于进程退出码判断，从而保留
`error.code`、`error.subtype` 和 `error.retryable` 等结构化信息。

权限错误继续映射为 `VOICE_SCOPE_MISSING`。识别接口仅在同时满足以下条件时映射为
内部可重试限流：错误码为 `99991400` 或 subtype 为 `rate_limit`，且
`error.retryable === true`。字段缺失、`null`、其它值和明确的 `false` 均不重试。
其它非零退出、无效 JSON 和 API 错误也不重试。

### 有界重试

识别调用默认最多追加三次重试，退避间隔依次为 `1000ms`、`3000ms`、`7000ms`。
初次调用加三次重试最多执行四次识别请求。退避只包围识别 API，不重新下载资源、
运行 FFmpeg 或重建 PCM 数据。

重试间隔和等待函数作为 `VoiceTranscriber` 的可注入依赖，生产环境使用固定默认值，
测试使用零等待替身。固定间隔便于验证，也避免增加随机数和配置项。

任一重试成功后照常返回识别文本。限流重试耗尽后抛出 `VOICE_RATE_LIMITED`；Gateway
回复“飞书语音识别服务当前限流，请稍后重试或改用文字。”。不可重试错误立即沿用
现有错误映射，不消耗后续重试次数。

## 数据流

```text
audio 事件
  -> 下载一次语音资源
  -> FFmpeg 转码一次
  -> 写入一次识别请求体
  -> 调用识别 API
     -> 成功：返回文字
     -> 可重试限流：按 1s / 3s / 7s 退避后重试
     -> 限流耗尽：VOICE_RATE_LIMITED + 明确提示
     -> 权限或其它错误：立即失败，不重试
  -> 清理临时目录
```

## 测试

- 非零退出且 stderr 包含缺少 scope 信封时，映射为 `VOICE_SCOPE_MISSING`。
- 首次限流、后续成功时，只下载和转码一次，并返回识别文本。
- 连续四次限流时，只等待三次并返回 `VOICE_RATE_LIMITED`。
- `retryable` 为 `false`、缺失或非布尔值，以及非限流 API 错误均不重试。
- stdout 成功信封仍按原路径解析，stderr 中的非 JSON 文本不会暴露给用户。
- `voiceFailureText` 对 `VOICE_RATE_LIMITED` 返回明确中文提示。
- 运行 `lark-claude` 全量 Node 测试，确认 post 路由、Session 续接和语音原流程无回归。

## 非目标

- 不建立持久化语音重试队列，不跨 Gateway 重启恢复识别请求。
- 不绕过飞书限流，不切换第三方语音识别供应商。
- 不改变音频时长、文件大小、格式、权限和发送者白名单规则。
- 不在日志中保存音频正文、base64 请求体或完整飞书错误响应。

## 验收

- 短暂限流在最多三次退避重试内恢复时，用户正常收到转写并继续执行指令。
- 持续限流时，用户收到明确的限流提示，而不是通用失败文案。
- 下载和转码在整个重试过程中各执行一次。
- 非限流错误不会因本修复产生额外请求。
- 全量自动化测试通过，Gateway 重启后 `listenerReady=true`。
